# Измерения, метрики и ловушки Reporting API

Справочник читается по потребности: имена — когда собираете запрос, ловушки — прежде чем
назвать число человеку.

Полный официальный справочник (351 КБ) — [`dim_all`](https://yandex.ru/dev/metrika/ru/stat/attrandmetr/dim_all.md).
У любой страницы документации Яндекса есть машиночитаемая версия: допишите `.md` к адресу.
Индекс всей документации — [`llms.txt`](https://yandex.ru/dev/metrika/ru/llms.txt).

## Семь пространств имён

| Префикс | О чём | Примечание |
| --- | --- | --- |
| `ym:s:` | Визиты (сессии) | Основное. Здесь визиты, отказы, источники, цели |
| `ym:pv:` | Просмотры страниц (хиты) | Всего 10 метрик; ни отказов, ни визитов, ни целей тут нет |
| `ym:ad:` | Клики Яндекс Директа | Требует `direct_client_logins`, иначе 403 `access_denied` |
| `ym:ev:` | Рекламные расходы | Свои группировки `ym:ev:<attribution>Expense*` |
| `ym:ep:` | Параметры событий | `ym:ep:actionGoal`, `ym:ep:eventParamsLevel1…10` |
| `ym:up:` | Параметры посетителей | `ym:up:paramsLevel1…5` |
| `ym:dl:` | Загрузки файлов | `ym:dl:downloadURL`, `ym:dl:pageURL`, `ym:dl:title` |

⚠️ **Пространства `ym:u:` не существует.** Параметры посетителя — это `ym:up:`. Имя `ym:u:`
встречается в чужих шпаргалках и в Logs API, но в Reporting API его нет.

**Правило смешивания: в `dimensions` и `metrics` одного запроса допустим ровно один префикс.**
Нарушение — честный отказ: HTTP 400, `error code 4011`, «Metrics and dimensions with different
prefixes can be used together only when filtering data».

**Исключение — `filters`.** Туда чужой префикс класть можно, и это штатный способ считать
визиты по условию на просмотры:

```
metrics=ym:s:visits & filters=ym:pv:URL=@'catalog'
```

## Имена, которыми отвечают на обычные вопросы

Имена **регистрозависимы**: `ym:s:pageViews` с заглавной V — это 400 `code 4002`, верно
`ym:s:pageviews`.

### Метрики визитов (`ym:s:`)

| Имя | Что это |
| --- | --- |
| `ym:s:visits` | Визиты |
| `ym:s:users` | Уникальные посетители |
| `ym:s:newUsers` | Новые посетители |
| `ym:s:pageviews` | Просмотры страниц внутри визитов |
| `ym:s:bounceRate` | Доля визитов с одним просмотром короче 15 секунд |
| `ym:s:pageDepth` | Среднее число просмотров за визит |
| `ym:s:avgVisitDurationSeconds` | Средняя длительность визита |
| `ym:s:percentNewVisitors` | Доля посетителей, у которых это первый визит за всю историю |
| `ym:s:robotPercentage` | Доля роботов — им и проверяется, насколько важен отсев |

### Группировки визитов (`ym:s:`)

**Источники.** `ym:s:trafficSource` (значения: `internal`, `direct`, `referral`, `organic`,
`ad`, `saved`, `external`, `email`, `social`, `recommend`, `messenger`, `qrcode`, `undefined`),
`ym:s:sourceEngine` (второй уровень), `ym:s:advEngine` (рекламная система),
`ym:s:referalSource` (переход с сайта), `ym:s:searchEngineRoot`, `ym:s:searchPhrase`.

**UTM.** `ym:s:UTMSource`, `ym:s:UTMMedium`, `ym:s:UTMCampaign`, `ym:s:UTMContent`, `ym:s:UTMTerm`.

**Страницы.** `ym:s:startURL` (вход), `ym:s:endURL` (выход), уровни `ym:s:startURLPathLevel1…5`,
`ym:s:referer`, `ym:s:refererDomain`.

**Техника и гео.** `ym:s:deviceCategory` (`desktop`, `mobile`, `tablet`, `tv`), `ym:s:browser`,
`ym:s:operatingSystem`, `ym:s:mobilePhone`, `ym:s:regionCountry`, `ym:s:regionCity`,
`ym:s:regionArea`.

**Время и признаки.** `ym:s:date` (`YYYY-MM-DD`), `ym:s:dateTime` (в поясе счётчика),
`ym:s:isNewUser`, `ym:s:isRobot` (значения `Yes` / `No`).

### Просмотры страниц (`ym:pv:`)

Метрик всего десять, ходовые: `ym:pv:pageviews`, `ym:pv:users`.
Группировки: `ym:pv:URL`, `ym:pv:title` (**не** `pageTitle`), `ym:pv:URLPathLevel1…5`,
`ym:pv:URLDomain`, `ym:pv:date`.

Вопрос «на какие страницы заходят» — это `ym:pv:`. Вопрос «сколько было визитов» — `ym:s:`.

### Электронная коммерция (`ym:s:`)

`ym:s:ecommercePurchases` — заказы; `ym:s:ecommerce<currency>ConvertedRevenue` — доход;
`ym:s:ecommerce<currency>ConvertedRevenuePerPurchase` — средний чек. Валюта подставляется
в имя: `ym:s:ecommerceRUBConvertedRevenue`. Товарные группировки: `ym:s:productName`,
`ym:s:productID`, `ym:s:productBrand`, `ym:s:productCategoryLevel1…5` (имени
`ym:s:productCategory` без уровня не существует).

## Цели

Идентификатор цели подставляется **прямо в имя, без скобок**:

| Форма | Что считает |
| --- | --- |
| `ym:s:goal<id>reaches` | Число достижений во всех визитах |
| `ym:s:goal<id>visits` | Визиты с достижением |
| `ym:s:goal<id>users` | Уникальные посетители, достигшие цели |
| `ym:s:goal<id>conversionRate` | Доля целевых визитов |
| `ym:s:goal<id>userConversionRate` | Доля достигших среди посетителей |

Агрегаты по всем целям: `ym:s:anyGoalReaches`, `ym:s:anyGoalVisits`, `ym:s:anyGoalUsers`,
`ym:s:anyGoalConversionRate`.

Фильтр по факту достижения — `ym:s:goal<id>IsReached=='Yes'`. Его нет в справочнике `dim_all`
вовсе, он документирован только в разделе про сегментацию, но работает.

Список целей счётчика — `call metrika_goal_list --counterId <ID счётчика>`.
Несуществующий идентификатор цели даёт честный 400 `code 4002`, а не пустой отчёт.

## Фильтры

Форма: `атрибут оператор 'значение'`. Строка требует URL-кодирования.

Операторов четырнадцать: `==`, `!=`, `>`, `>=`, `<`, `<=`, `=@` (подстрока), `!@`,
`=~` (регулярное выражение), `!~`, `=*` (со звёздочкой), `!*`, `=.` (входит в список), `!.`.
Список пишется в скобках: `ym:s:trafficSource=.('organic','direct')`.
Для метрик доступны только `==`, `!=`, `<`, `<=`, `>`, `>=`.

Множества: `EXISTS(...)`, `ALL(...)`, `NONE(...)` — «хотя бы один просмотр визита», «все»,
«ни один». Без явного оператора применяется `EXISTS`.

Пределы одного запроса: до 10 группировок и метрик суммарно, до 20 фильтров, строка фильтра
до 10 000 символов, до 100 значений в одном условии.

⚠️ Фильтры по группировкам и по метрикам комбинируются **только на верхнем уровне и только
через `AND`**.

## Ловушки: HTTP 200 и неверное число

Всё в этом разделе не даёт ошибки. Отчёт приходит нормальный, числа правдоподобные.

### Роботы не отсекаются сами

API отдаёт визиты вместе с роботами. Доля бывает какой угодно — измеряется метрикой
`ym:s:robotPercentage` в том же запросе. Отсекает фильтр `ym:s:isRobot=='no'`; значение
нечувствительно к регистру (`'no'` и `'No'` дают одно и то же — проверено запросом).

Команда ставит этот фильтр сама и пишет об этом в `_meta.applied_by_server`.

### Атрибуция: два написания, два разных числа

`ym:s:trafficSource` и `ym:s:<attribution>TrafficSource` читаются как синонимы, но
подставляют разные модели, и оба возвращают 200.

**Документация обещает, что `attribution` по умолчанию `last`, — и это не так.** В эхо-запросе
(`data.query.attribution`) приходит `CROSS_DEVICE_LAST_SIGNIFICANT`. Верить надо ответу, а не
доке: модель, по которой посчитан отчёт, всегда написана в `query.attribution`.

Актуальные значения: `cross_device_first`, `last`, `cross_device_last_significant`, `automatic`.
Устаревшие (`first`, `lastsign`, `last_yandex_direct_click`) **не отвергаются**, а с 25.06.2026
молча подменяются ближайшими аналогами — запрос, написанный год назад, продолжает работать
и считает другую модель.

Смена модели почти не двигает `totals`, но перекраивает разрезы: доля рекламы между моделями
меняется в разы. «Сумма сошлась» здесь ничего не доказывает — модель надо называть рядом
с числом.

### `lang` по умолчанию `en`, и фильтр по русскому названию даёт ноль

`ym:s:regionCityName=='Москва'` без `lang=ru` вернёт 200 и пустой результат. Пустой результат
фильтра неотличим от «такого сегмента нет».

Лечение: фильтровать по **идентификаторам**, а не по расшифровкам —
`ym:s:trafficSource=='organic'`, а не `ym:s:trafficSourceName=='Переходы из поисковых систем'`.

### Фильтр по метрике не меняет `totals`

Фильтр по группировке применяется к исходным данным и `totals` пересчитывает. Фильтр по
метрике применяется к **уже сгруппированным строкам** и `totals` не трогает: строки в ответе
не складываются в итог, и разница выглядит как ошибка счёта.

### Семплирование включается само

`accuracy` по умолчанию `medium`. Признак — поля `sampled`, `sample_share`, `sample_size`,
`sample_space`; сами числа никак не помечены. Косвенный признак — дробное значение
целочисленной метрики.

`accuracy=full` даёт полную выборку и **не требует Метрики Про** (проверено на обычном счётчике).

Семплирование сильнее бьёт по хвосту, чем по итогу: агрегат может ошибиться на доли процента,
а редкие URL и фразы просто не попадут в отчёт — не нулями, а отсутствующими строками.

### `total_rows` округляется

Поле `total_rows_rounded` говорит об этом прямо. Использовать `total_rows` как «сколько всего
уникальных значений» или как границу цикла пагинации нельзя — число зависит ещё и от `accuracy`.

### Строки не складываются в `totals`

`include_undefined` по умолчанию выключен, и визиты с неопределённой группировкой в строки не
попадают, хотя в `totals` учтены. Плюс `ym:s:users` и другие уникальные метрики **неаддитивны
в принципе**: сумма по строкам всегда больше итога, потому что один посетитель попадает
в несколько строк.

### Часовой пояс — счётчика, а не ваш

`date1`/`date2`, `today`, `yesterday`, `NdaysAgo` резолвятся в поясе счётчика. Поле `timezone`
появляется в эхо-запросе, только если вы его передали, поэтому по ответу пояс не восстановить.
При сверке с базой в UTC расхождение по суткам гарантировано.

`date2=today` тянет неполные текущие сутки. Развёрнутые даты всегда есть в `query.date1` и
`query.date2` — их и надо называть в ответе.

### `bytime` без `row_ids` рисует только семь верхних

Действует `top_keys` со значением по умолчанию 7 (максимум 30). График «по всем источникам»
молча превращается в график по семи, и в ответе следа не остаётся.

### Данные малых выборок скрываются

Соцдем, страницы входа и поисковые фразы не отдаются, если посетителей в выборке меньше десяти.
Строки не приходят с пометкой — они просто отсутствуют. Единственный сигнал —
`contains_sensitive_data: true`.

### «Просмотры» — два разных числа

`ym:s:pageviews` и `ym:pv:pageviews` считают по-разному (визиты против хитов) и расходятся
на проценты. Оба запроса валидны.

## Квоты

30 запросов в секунду на IP, 3 параллельных и 5000 в сутки на пользователя, 200 за пять минут
на `/stat/v1/data`. Превышение — 429 с типом квоты в теле; 503 `backend_error` и 504 — повторять
позже. Команда повторяет 429 и 5xx сама и пишет число повторов в `_meta.retries`.

⚠️ Цикл пагинации по большому отчёту упирается в квоту раньше, чем в конец данных. Молча
пропущенная страница выглядит как полный результат.

## Как проверить имя, не гадая

```bash
# есть ли такой метод и какие у него параметры
npx -y yandex-metrika-mcp-server describe metrika_stat_data

# машиночитаемая документация Яндекса — допишите .md к любому адресу
curl -s https://yandex.ru/dev/metrika/ru/stat/attrandmetr/dim_all.md | grep -i 'ym:s:bounce'
```

Ошибка в имени метрики или группировки — это 400 с кодом `4002` и точным указанием, что не так.
Опасны не они, а перечисленное выше: там ответ приходит нормальный.
